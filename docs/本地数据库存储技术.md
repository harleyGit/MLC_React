# **React 本地数据库存储系统技术方案（Tech Spec）**

适用工程：MLC_React ｜ 技术栈：React + JavaScript + IndexedDB + WebSocket + Go Backend

## **一、总体设计方案**

针对你的 React 工程，建议设计一套**统一的客户端本地数据持久化系统（Client Local Persistence System）**，用于聊天、商城、消息中心、运维管理、个人中心等业务模块。

核心目标是：

1. **SQL 风格的数据结构**：按照关系型数据库的思想设计数据表、主键、索引、查询条件和版本迁移。
2. **浏览器原生优先**：使用浏览器自身 API，尽量不引入第三方 SDK。
3. **支持实时消息持久化**：WebSocket 接收验证码、聊天消息、系统通知后写入本地数据库。
4. **支持多用户数据隔离**：不同账号登录同一个浏览器，不会读取到其他账号的个人数据。
5. **支持离线读取**：页面刷新、断网、重新打开浏览器后，仍然能够读取已缓存的数据。
6. **支持动态扩展**：未来增加订单、购物车、草稿、浏览记录、设备信息等模块，无须推翻现有架构。
7. **支持数据同步与生命周期管理**：处理重复消息、增量同步、缓存过期、登出清理和数据库升级。

## **二、技术选型**

首先需要明确：**普通 React Web 工程不能直接使用浏览器内置的 SQLite 或 MySQL。**

浏览器提供的是 IndexedDB，而不是传统 SQL 数据库。

| 技术           | 是否原生               | SQL 查询 | 适用场景                         | 建议     |
| -------------- | ---------------------- | -------- | -------------------------------- | -------- |
| IndexedDB      | 是                     | 不支持   | 用户、消息、订单缓存等结构化数据 | **首选** |
| localStorage   | 是                     | 不支持   | 少量非敏感 UI 状态               | 辅助     |
| sessionStorage | 是                     | 不支持   | 临时会话状态                     | 辅助     |
| SQLite WASM    | 否                     | 支持     | 必须执行 SQL 的 Web 应用         | 暂不引入 |
| OPFS           | 是（受浏览器支持限制） | 不支持   | 大文件及 SQLite WASM 文件存储    | 按需使用 |

### **推荐架构**

**React 业务模块**

聊天 · 商城 · 消息中心 · 运维管理 · 个人中心

**LocalDataService（统一本地数据服务）**

查询 · 写入 · 删除 · 事务 · 缓存策略 · 账号隔离

**IndexedDB**

持久化数据表及索引

**Memory Cache**

高频读取的内存数据

**Sync Engine（数据同步引擎）**

WebSocket 实时接收 · HTTP 增量同步 · 断线恢复

**MLC_GO 后端服务**

MySQL · Redis · Kafka · Centrifugo · 业务服务

**重要原则：**

- Go 后端 MySQL 是业务权威数据源（Source of Truth）。
- React IndexedDB 是本地数据副本（Local Replica），不应成为订单、支付、权限等业务数据的最终依据。
- 浏览器本地数据可能被用户删除或被浏览器清理，因此必须允许从服务器重新构建。
- Token 等敏感凭据不建议明文持久化在 IndexedDB 中，后面单独设计。

## **三、本地数据库表结构设计**

建议数据库名称：

`MLC_CLIENT_DB`

初始数据库版本：

`1`

浏览器 IndexedDB 中的 Object Store，可以理解为关系型数据库中的一张表，但它不提供 SQL 外键、JOIN 和完整的关系约束。

### **3.1 统一数据表规划**

| 表名（Object Store）    | 业务模块 | 用途                           |
| ----------------------- | -------- | ------------------------------ |
| `user_profiles`         | 个人中心 | 昵称、头像、用户基本信息       |
| `user_preferences`      | 个人中心 | 主题、语言、通知偏好           |
| `auth_sessions`         | 登录认证 | 非敏感登录会话元数据           |
| `verification_messages` | 消息中心 | WebSocket 接收的验证码通知记录 |
| `im_conversations`      | 聊天     | 会话列表、未读数量             |
| `im_messages`           | 聊天     | 文字、图片、语音消息元数据     |
| `notification_messages` | 消息中心 | 系统通知、订单通知             |
| `mall_products`         | 商城     | 商品列表与详情缓存             |
| `mall_cart`             | 商城     | 本地购物车副本                 |
| `mall_orders`           | 商城     | 订单展示缓存                   |
| `ops_task_cache`        | 运维管理 | 运维任务及状态缓存             |
| `sync_cursors`          | 数据同步 | 各业务模块同步游标             |
| `client_settings`       | 系统     | 非敏感客户端配置               |

其中，`verification_messages` 存储的是收到的验证码通知记录，而非长期保存可用于认证的明文验证码。验证码正文可以短暂显示，但应限制保留时间，并避免将其持久化。

| 字段         | 类型   | 说明                           |
| ------------ | ------ | ------------------------------ |
| `user_id`    | string | 用户 ID                        |

| `updated_at` | number | 最近同步时间                   |

同步游标是客户端实现断线恢复和增量同步的重要基础。

```

```
PRIMARY KEY (user_id, message_id)
```

### **5.2 创建并初始化数据库**

`HGDatabase.js`

```

import {
  HG_DB_NAME,
  HG_DB_VERSION,
  HG_SCHEMA
} from "./HGDatabaseSchema";

let dbPromise = null;

export function hgOpenDatabase() {
  if (dbPromise) return dbPromise;

  dbPromise = new Promise((resolve, reject) => {
    const request = indexedDB.open(
      HG_DB_NAME,
      HG_DB_VERSION
    );

    request.onupgradeneeded = () => {
      const db = request.result;
      const tx = request.transaction;

      for (const schema of HG_SCHEMA) {
        let store;

        if (!db.objectStoreNames.contains(schema.name)) {
          store = db.createObjectStore(schema.name, {
            keyPath: schema.keyPath
          });
        } else {
          store = tx.objectStore(schema.name);
        }

        for (const [name, keyPath] of schema.indexes) {
          if (!store.indexNames.contains(name)) {
            store.createIndex(name, keyPath);
          }
        }
      }
    };

    request.onsuccess = () => {
      const db = request.result;

      db.onversionchange = () => {
        db.close();
        dbPromise = null;
      };

      resolve(db);
    };

    request.onerror = () => {
      reject(request.error);
    };

    request.onblocked = () => {
      console.warn("数据库升级被其他页面阻塞");
    };
  }).catch(error => {
    dbPromise = null;
    throw error;
  });

  return dbPromise;
}

```

初始化调用：

```
import { hgOpenDatabase } from "./infrastructure/database/HGDatabase";

hgOpenDatabase()
  .then(() => console.log("本地数据库初始化成功"))
  .catch(console.error);
```

生产环境中，建议在应用启动层统一初始化，并提供初始化失败、数据库升级阻塞的 UI 状态。

### **5.3 封装通用数据库操作**

`HGBaseRepository.js`

```

import { hgOpenDatabase } from "./HGDatabase";

export class HGBaseRepository {
  constructor(storeName) {
    this.storeName = storeName;
  }

  async execute(mode, operation) {
    const db = await hgOpenDatabase();

    return new Promise((resolve, reject) => {
      const tx = db.transaction(this.storeName, mode);
      const store = tx.objectStore(this.storeName);

      let result;
      let settled = false;

      tx.oncomplete = () => {
        if (!settled) {
          settled = true;
          resolve(result);
        }
      };

      tx.onerror = () => {
        if (!settled) {
          settled = true;
          reject(tx.error);
        }
      };

      tx.onabort = () => {
        if (!settled) {
          settled = true;
          reject(tx.error || new Error("事务中止"));
        }
      };

      try {
        const request = operation(store);

        request.onsuccess = () => {
          result = request.result;
        };
      } catch (error) {
        settled = true;
        try {
          tx.abort();
        } catch {
          // 事务可能已结束
        }
        reject(error);
      }
    });
  }

  put(data) {
    return this.execute(
      "readwrite",
      store => store.put(data)
    );
  }

  get(key) {
    return this.execute(
      "readonly",
      store => store.get(key)
    );
  }

  delete(key) {
    return this.execute(
      "readwrite",
      store => store.delete(key)
    );
  }

  getAll() {
    return this.execute(
      "readonly",
      store => store.getAll()
    );
  }

  getAllByIndex(indexName, value) {
    return this.execute("readonly", store => {
      return store.index(indexName).getAll(value);
    });
  }
}

```

这样就实现了类似 Go Repository 的封装。

| Go / MySQL                 | React / IndexedDB  |
| -------------------------- | ------------------ |
| `INSERT` / `UPDATE`        | `put()`            |
| `SELECT WHERE primary_key` | `get()`            |
| `DELETE`                   | `delete()`         |
| `SELECT *`                 | `getAll()`         |
| `CREATE INDEX`             | `createIndex()`    |
| `BEGIN TRANSACTION`        | `db.transaction()` |

需要注意：`put()` 是覆盖式插入或更新（upsert），而 `add()` 是仅插入，遇到重复主键会报错。

## **六、用户信息与偏好存储**

### **6.1 用户信息 Repository**

`HGUserRepository.js`

```

import { HGBaseRepository } from "../../infrastructure/database/HGBaseRepository";
import { HG_STORES } from "../../infrastructure/database/HGDatabaseSchema";

class HGUserRepository extends HGBaseRepository {
  constructor() {
    super(HG_STORES.USERS);
  }

  async saveProfile(profile) {
    if (!profile.user_id) {
      throw new Error("user_id 不能为空");
    }

    return this.put({
      ...profile,
      cached_at: Date.now()
    });
  }

  async getProfile(userId) {
    return this.get(userId);
  }

  async removeProfile(userId) {
    return this.delete(userId);
  }
}

export const hgUserRepository = new HGUserRepository();

```

  updated_at: Date.now()
});

### **6.2 个人偏好存储**

`HGPreferencesRepository.js`

```

import { HGBaseRepository } from "../../infrastructure/database/HGBaseRepository";
import { HG_STORES } from "../../infrastructure/database/HGDatabaseSchema";

class HGPreferencesRepository extends HGBaseRepository {
  constructor() {
    super(HG_STORES.PREFERENCES);
  }

  async setPreference(userId, key, value) {
    return this.put({
      user_id: userId,
      key,
      value,
      updated_at: Date.now(),
      sync_status: "local"
    });
  }

  async getPreference(userId, key) {
    const record = await this.get([userId, key]);
    return record?.value;
  }

  async getPreferences(userId) {
    const records = await this.getAllByIndex(
      "user_id",
      userId
    );

    return Object.fromEntries(
      records.map(item => [item.key, item.value])
    );
  }
}

export const hgPreferencesRepository =
  new HGPreferencesRepository();

```

使用：

```
await hgPreferencesRepository.setPreference(

  "dark"

);

### **7.2 WebSocket 消息协议**

建议 Go 后端统一消息信封：

```
{
  "event_id": "evt_100001",
  "event_type": "verification.received",
  "user_id": "hgid_10001",
  "server_seq": "10001",
  "created_at": 1795000000000,
  "payload": {
    "message_id": "verify_10001",
    "purpose": "login",
    "display_text": "您收到一条登录验证码通知",
    "expires_at": 1795000300000
  }
}
```

**注意：** 这里不包含明文验证码。服务端应只将验证码发送到已经认证、且符合安全策略的指定会话；如果业务确实需要展示动态验证码，建议仅在内存中短暂保留，过期立即清除。

### **7.3 WebSocket 客户端**

`HGWebSocketClient.js`

```

export class HGWebSocketClient {
  constructor({ url, onMessage, onReconnect }) {
    this.url = url;
    this.onMessage = onMessage;
    this.onReconnect = onReconnect;

    this.socket = null;
    this.timer = null;
    this.retryCount = 0;
    this.stopped = true;
    this.generation = 0;
  }

  connect() {
    this.stopped = false;
    this.generation += 1;

    const generation = this.generation;
    this.open(generation);
  }

  open(generation) {
    if (this.stopped || generation !== this.generation) {
      return;
    }

    const socket = new WebSocket(this.url);
    this.socket = socket;

    socket.onopen = () => {
      if (generation !== this.generation) return;

      const wasReconnect = this.retryCount > 0;
      this.retryCount = 0;

      if (wasReconnect) {
        this.onReconnect?.();
      }
    };

    socket.onmessage = event => {
      if (generation !== this.generation) return;

      try {
        const data = JSON.parse(event.data);
        Promise.resolve(this.onMessage?.(data))
          .catch(console.error);
      } catch (error) {
        console.error("消息解析失败", error);
      }
    };

    socket.onclose = () => {
      if (this.stopped || generation !== this.generation) {
        return;
      }

      const delay = Math.min(
        1000 * (2 ** this.retryCount),
        30000
      );

      this.retryCount = Math.min(this.retryCount + 1, 10);

      this.timer = setTimeout(() => {
        this.open(generation);
      }, delay);
    };

    socket.onerror = () => {
      // 错误处理与重连交给 onclose
    };
  }

  disconnect() {
    this.stopped = true;
    this.generation += 1;

    clearTimeout(this.timer);
    this.timer = null;

    this.socket?.close();
    this.socket = null;
  }
}

```

生产环境还需要补充心跳策略、网络恢复、认证过期处理、消息大小限制和重连随机抖动。浏览器原生 WebSocket 不允许任意设置 HTTP Authorization Header，建议使用服务端校验的安全 Cookie 或短期连接票据，而不是把长期 Token 放入 URL。

如果使用 Centrifugo，其订阅、认证、恢复和消息格式需要遵循 Centrifugo 协议，不能直接假设上面的自定义 JSON 信封就是 Centrifugo 的原始 WebSocket 帧。可在服务端适配，或在确有必要时引入官方客户端 SDK。

## **八、聊天、商城等业务的存储策略**

不建议所有业务数据都使用同一种缓存策略。

| 业务       | 本地存储内容             | 缓存策略               | 服务端同步 |
| ---------- | ------------------------ | ---------------------- | ---------- |
| 用户信息   | 昵称、头像、简介         | Cache First + 后台刷新 | 是         |
| 用户偏好   | 主题、语言、字号         | Local First            | 按设置决定 |
| 聊天消息   | 消息内容、会话、发送状态 | 本地分页 + 增量同步    | 是         |
| 验证码通知 | 脱敏通知元数据           | 短期存储               | 按需       |
| 系统通知   | 通知标题、内容、已读状态 | 本地缓存 + 增量同步    | 是         |
| 商品列表   | 商品摘要、图片 URL       | TTL 缓存               | 是         |
| 商品详情   | 商品描述、规格           | TTL + 版本校验         | 是         |
| 购物车     | SKU、数量、选中状态      | 本地即时更新           | 是         |
| 订单       | 订单摘要、状态           | 服务端优先             | 是         |
| 运维管理   | 任务摘要、非敏感状态     | 短期缓存               | 是         |

### **8.1 聊天消息**

推荐使用**基于索引的游标分页**，不要每次读取全部聊天记录。

例如：

```
const index = store.index("conversation_time");

const range = IDBKeyRange.bound(
  [userId, conversationId, 0],
  [userId, conversationId, Number.MAX_SAFE_INTEGER]
);

const request = index.openCursor(range, "prev");
```

使用 `openCursor()` 每次取 20 ～ 50 条，避免单个会话有几十万条消息时将全部数据加载到内存。

消息去重使用服务端 `message_id`；发送中的消息另设 `client_message_id`，用于客户端重试和服务端确认后的关联。

### **8.2 商品缓存**

商品价格、库存、优惠券、会员折扣可能随时变化。

因此：

- 商品列表可以从 IndexedDB 快速展示。
- 商品详情进入页面时可以后台更新。
- **下单时必须重新请求 Go 后端计算价格、库存和优惠。**
- 不能使用本地 IndexedDB 中的价格直接生成最终支付订单。

### **8.3 运维管理**

运维模块可能包含权限、服务器状态、日志和敏感操作记录。

建议只缓存允许离线展示的非敏感摘要。管理员权限、MFA 状态、审批结果、服务器密钥等必须以 Go 后端实时校验为准，不能依据 IndexedDB 中的数据决定是否允许执行操作。

## **九、Token 与敏感数据的安全设计**

你提到需要存储用户 Token，这里需要单独处理。

**不建议将 Access Token、Refresh Token 明文写入 IndexedDB 或 localStorage。**

原因是：一旦 React 页面出现 XSS 漏洞，恶意 JavaScript 就可能读取这些数据。

推荐认证方案：

| 数据           | 存储位置                 | 原因             |
| -------------- | ------------------------ | ---------------- |
| Access Token   | JS 内存（可选）          | 降低长期暴露风险 |
| Refresh Token  | HttpOnly Cookie          | JS 无法直接读取  |
| 用户 ID        | IndexedDB                | 用于本地数据隔离 |
| 昵称、头像     | IndexedDB                | 普通业务缓存     |
| 登录状态元数据 | IndexedDB                | 仅供 UI 展示     |
| MFA 密钥       | 不存储在浏览器本地数据库 | 防止密钥泄露     |
| 用户偏好       | IndexedDB                | 支持持久化       |
| 验证码明文     | 优先仅存内存             | 避免敏感数据残留 |

建议由 Go 后端签发：

```
Set-Cookie: refresh_token=...;
  HttpOnly;
  Secure;
  SameSite=Lax;
  Path=/api/auth/refresh
```

以上为同站点部署示例，实际 Cookie 的 SameSite、Domain、Path 需要结合前后端部署域名决定。使用 Cookie 认证还需要考虑 CSRF 防护。

用户登出时应撤销服务端会话、关闭 WebSocket、清理内存凭据，并按隐私策略清理该用户的本地数据。

## **十、断线重连与增量同步**

仅靠 WebSocket 推送并不可靠，因为断网、浏览器休眠、关闭标签页都会造成消息遗漏。

建议设计：

```
         React 启动 / 网络恢复
                   |
                   v
             读取本地游标
                   |
                   v
         GET /api/sync?cursor=xxx
                   |
                   v
             Go Backend
                   |
          返回增量消息列表
                   |
                   v
          IndexedDB 事务写入
                   |
          +--------+--------+
          |                 |
       消息入库         更新同步游标
          |                 |
          +--------+--------+
                   |
                   v
             更新 React UI
                   |
                   v
          WebSocket 持续接收
```

推荐同步接口：

```
GET /api/v1/sync?domain=im&cursor=10001&limit=100
```

响应：

```
{
  "items": [
    {
      "message_id": "msg_10002",
      "conversation_id": "conv_001",
      "content": {
        "type": "text",
        "text": "你好"
      }
    }
  ],
  "next_cursor": "10002",
  "has_more": false
}
```

同步引擎必须满足：

1. **幂等写入**：相同消息重复接收，不产生重复记录。
2. **游标原子更新**：消息写入与同步游标更新应放在同一个 IndexedDB 事务中，防止消息未写入却提前推进游标。
3. **消息乱序处理**：以服务端序号判断顺序，不能只依赖客户端接收时间。
4. **断线补偿**：重新连接后主动执行增量同步。
5. **账号隔离**：切换用户后取消旧用户同步任务。
6. **分页同步**：通过 `has_more` 连续拉取，不能假设一次返回全部数据。

对于聊天消息，还需要服务端提供历史补拉、消息撤回、删除标记以及游标失效后的全量重建机制。

## **十一、数据库扩展与升级**

未来增加新的业务表，例如：

```
mall_favorites
mall_browsing_history
user_addresses
chat_drafts
media_upload_tasks
device_cache
ops_audit_summaries
```

不需要重新设计整个系统，只需要：

1. 在 `HGDatabaseSchema.js` 添加表结构。
2. 将 `HG_DB_VERSION` 从 `1` 升级为 `2`。
3. 在 `onupgradeneeded` 中创建新表或索引。
4. 为涉及数据变更的升级编写版本迁移逻辑。
5. 测试旧版本数据是否能够正常读取。

注意，前面的 `HGDatabase.js` 示例可以完成新增表和索引，但不包含删除旧索引、修改主键、数据转换等复杂迁移。生产环境应使用明确的版本迁移脚本，不能直接修改已经存在的 Object Store 主键。

### **数据容量管理**

浏览器存储不是无限的。建议：

- 使用 `navigator.storage.estimate()` 监控使用量。
- 使用 `navigator.storage.persist()` 申请持久化存储，但浏览器可能拒绝。
- 为商品、通知、聊天消息分别设置保留策略。
- 缓存头像和图片时优先保存 URL，不要默认把所有图片 Blob 存入数据库。
- 处理 `QuotaExceededError`，必要时优先清理可重新下载的商品缓存。
- 不依赖 IndexedDB 永久保存尚未上传的重要用户数据。

## **十二、React 与 IndexedDB 的数据更新机制**

IndexedDB 写入成功，不代表 React 会自动重新渲染。

因此需要增加一层数据变更通知机制：

```
   WebSocket / HTTP / 用户操作
               |
               v
         Repository
               |
               v
          IndexedDB
               |
               v
       HGLocalDataService
               |
       触发数据变更事件
               |
               v
          React Hook
               |
               v
          React 页面更新
```

推荐：

- 同一页面内：使用 React `useSyncExternalStore` 订阅统一数据状态。
- 多个标签页之间：使用浏览器原生 `BroadcastChannel` 通知其他标签页重新查询 IndexedDB。
- 大量数据变化时：合并通知，避免每条 WebSocket 消息都触发整个聊天列表重绘。
- WebSocket 生命周期：统一管理连接，不要在每个 React 页面各自建立连接。

`BroadcastChannel` 只用于传递数据变更通知，不应把 Token 或敏感消息正文放入广播。

## **十三、实施优先级**

建议分四期实施，避免一次性把全部业务模块耦合进来。

| 阶段 | 实施内容                                       | 验收标准                   |
| ---- | ---------------------------------------------- | -------------------------- |
| P0   | IndexedDB 初始化、Schema、Repository、版本管理 | 支持增删改查、刷新持久化   |
| P1   | 用户信息、偏好、验证码通知                     | 多账号隔离、WebSocket 入库 |
| P2   | 聊天消息、通知中心、同步引擎                   | 消息去重、分页、断线补拉   |
| P3   | 商城、运维、缓存清理、性能优化                 | TTL、容量管理、离线恢复    |

重点测试浏览器刷新、重复消息、账号切换、数据库升级、多标签页、断网重连和存储空间不足等场景。

## **十四、最终技术决策**

**本地数据库**

IndexedDB

**开发语言**

JavaScript ES Modules

**数据库操作**

原生 IndexedDB API

**实时通信**

WebSocket / Centrifugo

**多标签页通信**

BroadcastChannel

**React 数据订阅**

useSyncExternalStore

**数据同步**

HTTP Cursor + WebSocket

**第三方数据库 SDK**

暂不需要

**对于 MLC_React，我建议采用「IndexedDB + Repository + LocalDataService + SyncEngine」四层架构。**

这样既能保持原生 JavaScript 的轻量化，又能满足聊天、商城、消息中心、个人中心等模块的扩展需求。

需要特别区分：这套方案是**具备 SQL 表设计思想的浏览器本地数据库架构，而不是真正的 SQL 执行引擎**。如果你的硬性要求是直接执行 `SELECT`、`JOIN`、`UPDATE` 等 SQL 语句，则应改为 SQLite WASM + OPFS，代价是增加运行时、兼容性和文件管理复杂度。

以上代码构成基础实现骨架。要达到可上线状态，还需完成同步引擎、数据库迁移测试、账号清理、WebSocket 协议适配和异常恢复等部分。
